# Metadata and storage

## Rules from the subject

- The artwork contains the number **42**.
- The metadata `name` contains **42** and a title. The scripts always produce `42 - <title>`, and
  the on-chain contract refuses names without `42`.
- The artist is the 42 login **`maagosti`** (`ARTIST_LOGIN`, also stored in `artist()` in both contracts).
- The image is stored with a distributed technology: **IPFS** (mandatory) or the blockchain itself (bonus).

## Metadata JSON (ERC-721 Metadata JSON Schema + OpenSea fields)

```json
{
  "name": "42 - Best Bocal",
  "description": "42 - Best Bocal, an artwork by maagosti for TokenizeArt.",
  "artist": "maagosti",
  "created_by": "maagosti",
  "image": "ipfs://bafybeidgq3pfjrmxekjmxpjky5brgqifkpw6gaxjfc4emangn764okstg4",
  "attributes": [
    { "trait_type": "Artist", "value": "maagosti" },
    { "trait_type": "Storage", "value": "IPFS" }
  ]
}
```

This is the metadata of `Mokko42NFT` #1 ([`mint/metadata/42-best-bocal.json`](../mint/metadata/42-best-bocal.json)),
pinned at `ipfs://bafkreieutd5aybbgdymw2vpzfqiey45gvwyocnfguwokpdhlkb3b5lkacu`. It is generated by
[`code/scripts/metadata.cjs`](../code/scripts/metadata.cjs).

## IPFS (Mokko42NFT)

1. `make ipfs-upload` sends the image to IPFS through Pinata and gets back its CID, a hash of the content.
2. It writes the JSON above with `image = ipfs://<image CID>` and uploads it too, which gives the metadata CID.
3. `make mint` stores `ipfs://<metadata CID>` as the token's `tokenURI`.
4. The history of uploads is in [`mint/ipfs.json`](../mint/ipfs.json).

Because a CID is the hash of the file, nobody can change the image or the metadata behind a token:
different content would have a different CID. Pinata keeps the files pinned, so they remain available.
Any gateway can read them, for example `https://gateway.pinata.cloud/ipfs/<CID>`.

## On-chain (Mokko42Inscriptions)

The image bytes are kept in contract storage. `tokenURI` returns:

```
data:application/json;base64,eyJuYW1lIjoiNDIgLSBCZXN0IEJvY2FsIiwiZGVzY3JpcHRpb24iOi...
```

which decodes to the same JSON as above, with `image = data:image/webp;base64,...`, and the
attributes `Storage: On-chain` and `Finalized: Yes`. `make onchain-show` decodes it and writes the
image to [`mint/onchain/`](../mint/onchain/).

Images must stay small. Writing them costs gas per byte, and `tokenURI` too: it reads every byte
from storage and base64-encodes it twice (image, then JSON), about 240 gas per byte. RPC nodes cap
read-only calls (16.7M gas on publicnode), so the on-chain artwork is a 384×384 WebP of 28 236 bytes
(3 chunks, ~6.7M gas to read). `make onchain-mint` refuses images above 32 KB (`MAX_IMAGE_BYTES`).
